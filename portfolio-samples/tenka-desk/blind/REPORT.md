## 2. 一番大きな問題：合意状況ファイルが使われない

**何が起きたか**

- 合意状況ファイルには、得意先ごとに「前回の値上げに合意したか・見送ったか・いつから適用か」が書いてあります。
- アプリは、このファイルが**どの値上げ（改定日）の答えか**を決める必要があります。
- アプリは定価の履歴から改定日を探します。**改定日が1つだけ見つかったときだけ**、自動でつなげます。
- 2組とも、定価の履歴に改定日が3つありました。
  - gen-1：2025-04-16、2025-10-01、2026-04-01
  - gen-2：2024-10-01、2025-06-16、2026-03-01
- そのため、アプリはどれか決められず、ファイルを使いませんでした。
- すると、値上げを見送った得意先や、適用日を後ろにずらした得意先の**正しい旧価格**まで「反映漏れ」に見えます。

**画面での見え方**（コードを読んで確かめました。画面を動かしてはいません）

- 取り込み画面に、青い「お知らせ」が1つ出ます：「…どの定価改定の合意状況か決められないため、使っていません。改定日を指定してください。」
- 診断画面には、警告が出ません。ファイルがまったくないときに出る警告「前回改定の合意状況が読み込まれていません」は、ファイルを読み込んだだけで消える作りだからです。
- 2組とも `demo_settings.json` に `previousRevisionDate`（同梱サンプルと同じ名前）で前回の改定日を書いていました。アプリはこの項目を読みません。

**日付を入れると**

- アプリが計算した「正しい単価」が、正解と全行で一致しました（gen-1 20,569行、gen-2 20,661行）。入れる前は 19,800行と 19,688行でした。
- 食い違いは 1,740行から 8行に減りました。

**分類**：判定のルールは正しく、日付を入れると全部消えるので (d) 取り込みの問題としました。ただし、データの側の不備ではありません。アプリが「使っていない」ことを目立たせない作りの問題です。アプリの不具合として直します。

## 3. 言葉の説明

| 言葉 | 意味 |
|---|---|
| 正解 | 生成器が、文書（README など）のルールに従って1行ずつ決めた答え |
| 適合率 | アプリが「漏れ」と言った行のうち、本当に漏れだった行の割合。低いと**空振り**が多い |
| 再現率 | 本当の漏れのうち、アプリが見つけた行の割合。低いと**見逃し**が多い |
| 組 | 得意先 × 商品の組み合わせ |
| 金額（影響額） | 直近12か月（2025年7月〜2026年6月）の不足額の合計。予測ではない。4種類（反映漏れ・特値の期限切れ・掛率ランク外・粗利下限割れ）の合計で、原因不明の価格差は入れない（アプリも正解も同じ） |
| あいまいな行 | 文書のルールでは答えが決まらない、と生成器が判断した行。採点から外して、別に報告する（各組 89行） |
| ブラインド検証 | アプリの判定を先に出して残し、そのあとで正解を開けて答え合わせをすること |
| 生成器 | テスト用の架空データと正解を作るプログラム |

### (c) とした理由

**#8 無償の販促品（3行・33,296円）**

- `data-gen/README.md` は、見本品を「単価0で備考に『見本』『サンプル』」と書いています。gen-1 はこの文言どおりに読み、「販促品(無償提供)」は見本品ではない＝掛率ランク外の漏れ、としました。
- エンジンは「無償」「試供」も見本品とみなします。これは `docs/evaluation.md` に書いてありますが、生成器が読んでよい文書には入っていませんでした。
- gen-2 は、同じ書き方（0円で「販促品（無償提供）」）を「あいまい」にしています。2つの生成器でも読み方が分かれました。
- 商売としても、「無償で渡した販促品は値付けの漏れではない」とも、「タダで出した分は利益の漏れ」とも言えます。

**#9・#10 正しい単価より高い請求（5行）**

- `data-gen/README.md` の手順7は「ランクの下限〜上限の外 → 掛率ランク外」です。上に外れた場合も含む、と読めます。2つの生成器はこう読み、マイナスの不足額をつけました。
- エンジンは、正しい単価より高い請求を「基準より高い請求（要確認）」として別に数え、漏れの金額には入れません（`docs/evaluation.md` と `src/engine/diagnosis.ts` に書いてあります）。
- 「利益漏れ」は取り損ねたお金なので、高すぎる請求は漏れではない、という読み方にも筋が通ります。gen-2 も、これは文書で決まらないと注記に書いています。

### (b) が0の理由

10のまとまりすべてで、正解のラベルを `data-gen/README.md` の手順と照らしました。生成器はどれも文書の文言どおりにつけていて、文書と違う正解はありませんでした。

## 8. この検証の限界

- **生成器は2つだけです。** 2組で良い結果でも、ほかのデータで同じとは限りません。
- **正解の封印は、手順の上だけです。** 正解は同じ作業環境のフォルダに置き、ワークフローが「開けない」ことで守っていました。暗号で封をしたわけではありません。`SEALED.sha256` も、生成器が正解を作ったあとで自分で計算したものです。生成の前に第三者へ預けた約束ではありません。そのため、「採点の途中で正解を差し替えていない」ことは確かめられます。一方、「生成器がエンジンのコードを見ていない」「判定を出す前に正解を見ていない」ことは、作業の記録と申告に頼っています。
- **採点した側は、生成器の注記（`notes.md`）と README を読める状態でした。** 注記には、どこがあいまいかが書いてあります。6章の分類も、正解と注記を見たあとで、同じワークフローが行いました。
- **生成器もエンジンも、同じ系統のAIが書きました。** 文書の読み方のくせが似ている可能性があり、独立性は弱いです。
- **アプリの判定ファイルの指紋は、リポジトリに先に残していません。** 正解を開ける前に指紋を取った記録は作業ログにだけあります。代わりに、この報告を書くときにもう一度実行し、4つの判定ファイルがバイト単位で同じになることを確かめました（10章に指紋）。
- **「改定日あり」の日付は `demo_settings.json` から取りました。** 実際に使う人は、前回の改定日を自分で知っている必要があります。
- **正解は「文書をこう読んだ」という1つの答えです。** 実際の取引で正しいかとは別です。文書を書いたのも、このプロジェクトです。
- **反映チェック（gen-2 の `next/`）は採点していません。** gen-1 は B形式だけです。
  - 追記：直したブランチで採点を足しました（11章）。`results.json`・`mismatches.csv` もそのときに作り直しました。直す前のものはコミット 20004cd にあります。
- **実際の販売管理データでの精度は分かりません。**

**(a) とした理由**

- README の「判断が分かれる場面」では、反映漏れは「その得意先に直前まで適用されていた定価のまま」の請求です。
- 同じ表の「前回の改定を見送った得意先が、後の別の改定で定価が変わった商品を買った」の行は、その得意先の定価のつながり（見送った改定は飛ばす）で「直前の定価」を決めています。
- 「合意状況に行がない得意先」の行には「合意状況ファイルのない定価改定も、全得意先にこの扱い」とあります。gen-3 の README も、合意状況ファイルの改定より前の改定は、全得意先が新定価で請求する運用だった、と書いています（年は書いていません。定価の履歴では 2024-10-01 と 2025-10-01 です）。
- そのため、この得意先の定価は 2025-10-01 に 2,250円 → 2,400円になり、2026-04-01 のあとも 2,400円のままです。直前まで適用されていた定価は 2,250円で、2,250円 × 掛率での請求は反映漏れです。
- アプリ自身も、2026-04-01 の前は同じ組・同じ請求単価を反映漏れにしています。この得意先の定価は4月1日の前後で変わっていないのに、判定だけが変わります。
- コードでは、据え置き（見送り・協議中・据え置きカテゴリ・適用日前）のとき、`resolveList` が `previousPrice: null` で前の定価を捨てています（`src/engine/dataset.ts` 375〜383行）。そのため旧価格が計算されず、ランクの下限（1,872円）より安いので掛率ランク外になります。
- 生成器のコード（`blind/gen-3/lib/world.mjs`）は、得意先ごとに定価のつながりを作り、その1つ前を「前の定価」にしていました（ラベルを決めたあとで確かめました）。
- 同梱サンプルは前回の改定が1つだけなので、この形は出てきません。

gen-4 の生成器は、同じ形（見送りの得意先が、据え置いた定価のさらに1つ前の定価で請求）を「あいまい」にしていて（11行）、採点外です。gen-4 を見た採点者は、README の「2回前の定価」の行から掛率ランク外（読み方 B）寄りと読み、(c) としました。gen-3 を見た採点者は、上の理由で (a) としました。採点者の読み方が分かれたので、README に1文足すことを 12.9 に入れます。

**(b) とした理由**

- README は「得意先マスタにない得意先（諸口・現金売上など）」を対象外にする、と書いています。
- `data-gen/README.md` の「商品マスタにないコード」は、運賃など商品でないコードのことです。#2・#3 の商品は商品マスタにあります。
- 正しい答えは「対象外（マスタにない得意先）」で、#3 は返品でもあります。生成器のコード（`blind/gen-3/lib/judge.mjs`）は、マスタにない得意先の行にすべて「商品マスタにないコード」を付けていました。
- どちらの側も対象外にしているので、漏れの件数と金額には影響しません。`data-gen/README.md` には、この場合のラベルがありません（1回目の生成器は「あいまい」にしていました）。

**(d) とした理由**

## English summary

Blind test of the tenka-desk leak engine on two fictional datasets made by two independent generators (gen-1: 22,200 sales lines, B layout; gen-2: 21,953 lines, A and B layouts). The engine's labels were produced before the sealed truth was opened. All 5 truth files matched `SEALED.sha256`. Lines the truth marks ambiguous (89 per dataset) are left out of precision and recall. This PR only measures; it changes no engine or app code.

**As shipped (no input on the import screen):** the app reports about twice the true leak amount: ¥2,437,000 vs ¥1,308,014 (gen-1) and ¥16,746,079 vs ¥8,006,460 (gen-2). Line precision for any leak is 61.0% and 52.6%, and recall is 99.5% and 99.8%. Almost all false positives are "old price" leaks: 2.5× and 3.4× the true line count, and 3.1× and 3.2× the true amount. The cause is that the app does not use the previous revision's agreements file. It links that file to a revision only when the list-price history shows exactly one revision date, and both datasets have three. The import screen shows only an info-level note. The diagnosis screen shows no warning, because its "agreements file missing" warning goes away once the file is imported, even when the file is not used. Both datasets also give the date as `previousRevisionDate` in `demo_settings.json`, which the app does not read.

**With the revision date entered (the one thing the import screen asks for):** precision is 100% in both datasets. Recall is 99.5% (1,174/1,180) and 99.8% (1,077/1,079). Amounts are within +0.7% of the truth (+¥9,482 and +¥52,431). Label agreement is 22,105/22,111 and 21,862/21,864.

**Mismatch classes (10 clusters, 1,740 lines, default run):** (a) engine bug 0; (b) generator error 0; (c) docs ambiguous / both readings defensible 3 clusters, 8 lines (zero-price "販促品(無償提供)" treated as a free sample; billing above the expected price reported as "overcharge" instead of an out-of-tier leak); (d) import problem 7 clusters, 1,732 lines, all from the unused agreements file. Class (d) is not a rule error, but it is an app defect and must be fixed.

**Limits:** only two generators. The truth was sealed operationally by the workflow, not cryptographically before generation. The scorer could read the generators' notes and did the classification after the reveal. The generators and the engine were written by the same family of AI model. The engine-label hashes were not committed before the reveal, but a rerun reproduces all four label files byte for byte. The follow-up check (gen-2 `next/`) was not scored. Accuracy on real sales data is unknown.

**Follow-up (2026-10-17, branch `tenka-desk-revision-fix`, section 11):** items 1–7 below are fixed. Rerun on the same two sets with no date entered, the app now picks 2025-10-01 (gen-1) and 2025-06-16 (gen-2) itself, because the most common 適用日, the YYYY-MM in the file name and `previousRevisionDate` all point to the same history date; the default label files are now byte-identical to the earlier "revdate" files, so the default run matches the truth as closely as the revdate run did. The newly scored follow-up check (gen-2 `next/`) finds all 43 still-old-price lines with no false positives (¥343,236, equal to the truth) for both master layouts. These sets were already opened and the inference rule was designed after seeing them, so this is a regression check only; item 8 (a fresh blind set) is still open. After review (section 11.5): a file name with two year-months (a data period) no longer gives a revision signal; while the agreements file is unused, 仮 also marks expired-special and out-of-tier amounts and the printed letter (which then shows no "※ご請求" note); the generator's truth rule keeps the rank upper limit; the follow-up scoring has unit tests. The rerun reproduced every label file, `results.json` and `mismatches.csv` byte for byte.

**Recommended fixes (separate PR, then a fresh blind set):** (1) make an unused agreements file a visible warning on both screens, and mark old-price amounts as provisional until a date is set; (2) infer the revision date when exactly one history date matches the file's most common 適用日, the YYYY-MM in its name, or `previousRevisionDate`; (3) document the date step in the README; (4) align the docs on free goods and show their count and amount; (5) document that overcharges are not leaks; (6) list the engine's choice for each ambiguous pattern in one place; (7) score the follow-up check; (8) re-measure on new, unseen generators with the truth hash committed before the engine runs.

**Second blind round (2026-10-19, branch `tenka-desk-blind-2`, section 12):** three new generators written by different models (gen-3 Sonnet, gen-4 Fable, gen-5 Opus), truth hashes committed in 8da2a53 before the engine ran, no settings file with the revision date, no year-month in the agreements file names, and scorers who did not open the generators' notes. The engine was not changed. With no date entered, the app picked the right revision date in all three from the most common 適用日, so the default labels equal the date-entered labels byte for byte. Any-leak line precision / recall: gen-3 100% / 100%, gen-4 88.6% / 100%, gen-5 98.2% / 100%; no true leak was missed. Last-12-month amount, app vs truth: ¥4,298,373 vs ¥3,684,544, ¥3,874,843 vs ¥3,376,311, ¥807,621 vs ¥768,817 (the whole gen-3 gap is on lines the truth marks ambiguous). The follow-up check is 100% / 100% on scored lines with equal amounts in all three. The 385 scored mismatched lines are: (a) one engine bug, 10 lines — for a customer who kept an older list price, `resolveList` drops that list's predecessor, so billing at the predecessor shows as out-of-tier instead of old price (total amount unchanged; ¥31,018 moves between types; this is the gen-3 scorer's call, and the gen-4 scorer read the same shape, 11 unscored lines there, as ambiguous); (b) 176 lines where gen-3's truth gave the non-product label to customers missing from the master (both sides exclude them); (d) 199 lines from three agreement cells the importer did not read as written (適用日 「未定」 on two 協議中 rows in gen-4, a category name instead of its code in gen-5), each silently turning that customer into "agreed". Limits: one AI vendor, generators that read the same docs (which describe the engine's choices), fictional data, one agreements file answering one revision per set, and only the most-common-適用日 signal exercised for the revision date. The engine-label hashes were not committed before scoring (a rerun reproduces all six label and follow-up files byte for byte). The follow-up files are unchanged byte for byte. The "agreed with an undecided date" path does not occur in any of the five sets and is covered only by unit and screen tests. After review (section 13.8): any text in the 適用日 of a 協議中/見送り/対象外 row and any non-date 申入日/回答日 no longer drops the row; rows whose 得意先コード is blank, a name, or not in the customer master are reported; 「合意（適用日未定）」 with a blank 適用日 is read as undecided; warnings are shown only for used files and listed once; the same answer written two ways is no longer a conflict; and the 新単価マスタ export refuses a 協議結果 with an agreed 「未定」 date or an unmatched 対象外カテゴリ, reading category names as the diagnosis does. None of the five sets contains the newly handled cases, so they are covered only by unit and screen tests.
