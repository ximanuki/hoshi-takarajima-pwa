# 漏れ検出の評価（架空データ）

`src/engine` の利益漏れ検出と反映チェックを、サンプルデータの正解（`data-gen/truth/`）と比べた結果です。

## 先に結論

- 架空データでは、4種類の漏れすべてで適合率・再現率とも 100%、年間影響額も正解と1円単位で一致しました。
- ただし生成したサンプルは、生成器と同じ言葉づかい・同じ書き方でできていて、紛らわしい書き方（「合意に至らず」、Excel の日付、Shift_JIS など）を含みません。そこで、生成器とは別に**手で書いた小さな「崩れた」サンプル**（`scripts/messy-sample/`、18行）を用意し、別に採点しています（下の「手書きの崩れたサンプル」）。
- **これは実データでの精度を示す数字ではありません。** サンプルデータと検出ルールは同じプロジェクトで作っていて、どちらも `data-gen/README.md` に書いた同じ価格ルールにもとづいています。100% は「エンジンが文書化したルールどおりに動いている」ことの確認です。
- 実データでの精度は、実際の販売管理データで試すまでわかりません（下の「この評価でわからないこと」を参照）。

## 評価のしかた

```bash
npm run sample     # cd data-gen && npm run gen（public/sample/ と data-gen/truth/ を作る）
npm run evaluate   # node scripts/evaluate.ts（表を表示し、docs/evaluation-results.json に書き出す）
```

- エンジンが読むのは `public/sample/` の公開ファイルだけです。正解ファイルは `scripts/evaluate.ts` が採点のためだけに読みます。
- 売上明細 56,328行（2024年10月〜2026年9月）を、販売管理A形式とB形式のそれぞれで診断しました。2つの形式の結果は1行も違いませんでした。
- 「行」は売上明細1行ごと、「組」は得意先×商品×漏れの種類ごとの一致です。1行に複数の問題があるときは、エンジンの優先順（反映漏れ → 特値の期限切れ → 掛率ランク外 → 粗利下限割れ）で1つに決めて比べています。
- 年間影響額は直近12か月（2025年10月〜2026年9月）の不足額の合計です。
- 実行環境：Node.js 22.22.0。計算は整数だけで行い、時計・乱数・ロケールを使わないので、何度実行しても同じ結果になります。

### 手書きの崩れたサンプル（別に採点）

`scripts/messy-sample/` は、生成器を使わずに手で書いた架空の小さなデータです（得意先6社・商品4点・売上明細18行）。1行ずつ、期待する判定と理由を `truth.csv` に書いてあります。生成したサンプルにない、次のような書き方を入れています。

- 売上明細が Shift_JIS、原単価の列がない、最後に Excel が残す `,,,,` の行、摘要の中の改行
- `2025/11/10 0:00:00` のような時刻つきの日付、`R7年12月1日`、数量 `10.00`、`2-`（後ろにマイナス）、単価 `￥792`・`\792`（Shift_JIS の円記号）
- 合意状況が「合意に至らず」「未合意」「合意予定」「部分合意」
- 定価の値下げのあとに旧定価で請求、掛率ランクの上限を超える請求（どちらも利益漏れではなく「基準より高い請求」）
- 理由のわからない価格差、「送料5%引き当て」（値引ではない備考）、原単価の履歴が始まる前の行、7桁で先頭がゼロの得意先コード

| | 結果 |
|---|---|
| 読み込み | 18行すべて（Shift_JIS と判定、読み込みの問題 0件） |
| 判定の一致 | 18/18行 |
| 漏れ・原因不明の検出 | 適合率 100.0% / 再現率 100.0%（7行） |
| 基準より高い請求 | 2行（利益漏れの金額には含めない） |
| 読み替えた合意状況 | 4件（画面の「マスタの確認事項」に表示） |

参考までに、レビュー前のエンジン（コミット 9190b43）で同じサンプルを読むと、判定が一致したのは 18行中 3行でした。時刻つきの日付で定価の履歴が読めず、売上明細も6行が読み込めず（さらに Excel が残した空の行2行が「読めない行」として報告され）、「合意に至らず」などが合意として扱われ、「送料5%引き当て」が数量値引とみなされていました。

このサンプルも同じ人が書いたものなので、独立した検証ではありません。ここで確かめているのは、レビューで見つかった書き方の違いを読めることと、利益漏れでないものを漏れに数えないことです。

## 評価の途中で変えたこと

正直に記録しておきます。

- **漏れ検出のルールは、評価を見てから変えていません。** 最初の実行から上の表と同じ結果でした。ただし、ルールを書く前に `data-gen/lib/rules.ts`（正解の定義）と `data-gen/README.md` を読んでいます。そのため、この評価は独立した検証ではありません。
- **得意先まるごとの判定**：最初は「直近12か月に買った商品のうち、問題のある商品の割合」で判定していて、2026年2月に直った得意先（001251）を見落としました（47/75 = 63%）。「問題が続いていた期間に買った商品のうちの割合」に変えて、4社とも示せるようになりました（001251 は 64/73）。正解の得意先コードを使ったものではありませんが、評価結果を見てから変えた点です。
- **新単価マスタの現単価**：最初は直近の請求単価を使っていて、44行が違いました。特値が切れた後の単価を反映できていなかったためです。「漏れが続いている組は直近の請求単価、それ以外は正しい単価」に変えて、6行になりました。

## エンジンのルールと正解ルールの違い

エンジンは一般的なルールとして書いたので、正解ルールと少し違うところがあります。このデータでは結果に差が出ませんでした。逆にいうと、このデータはこれらの違いを試せていません。

このうち「基準より高い請求」と「無償品」は、ブラインド検証のあとで正解ルールをエンジンにそろえたので、今は違いがありません。

- 数量値引：値引後の単価の端数処理は、設定の単価の端数処理（初期設定は切り捨て）だけを認めます（正解ルールと同じ）。値引率は「値引」「割引」などの言葉のすぐ隣にあるものだけを読み、「値引なし」などは値引とみなしません。
- 粗利下限割れ：数量値引の行も粗利率を確かめます（正解ルールでは数量値引の行は正常）。このデータには該当行がありませんでした。
- 基準より高い請求：ランクの上限を超える請求や、定価の値下げのあとも旧定価で請求している行は、利益漏れではなく「基準より高い請求（要確認）」として別に数え、漏れの件数・金額・得意先単位の判定には入れません。ブラインド検証（`blind/REPORT.md`）のあと、正解ルール（`data-gen/lib/rules.ts`）もこの扱いにそろえました（`overcharge`）。サンプルにはこれに当たる行がないので、正解も結果も変わっていません。
- 定価の変更：合意状況の記録がない定価の値上げでも、旧定価のままの請求を反映漏れとして示します（値下げは対象外）。
- 無償品：単価0円で、備考に「見本」「サンプル」「無償」「試供」のどれかがある行を、見本品・無償品として対象外にします。ブラインド検証のあと、正解ルールも同じ4つの言葉にそろえました。サンプルの見本品はどれも「見本」「サンプル」と書いてあるので、正解も結果も変わっていません。診断の画面では、無償品の行数と定価で計算した金額を、利益漏れとは別に示します。
- 「継続中」：正解は「埋め込んだ漏れが直っていないか」で数えますが、エンジンは「その組の最後の請求がまだ漏れか」で判断します。反映漏れの継続中は、正解 132組に対してエンジン 145組です。直った後に売れていない組は、データからは直ったかどうかわからないためです。

## この評価でわからないこと

- 実際の販売管理データでの精度。実データには、このサンプルにない状況がありえます。
  - 価格改定が何度も重なる、期間の途中で単価が変わる、得意先の掛率が途中で変わる
  - 単価に小数がある（銭単位）、重さや長さで売る商品、税込単価
  - 値引やリベートが別の行や後日の伝票で計上される
  - 店舗別・納品先別の単価、同じ商品の複数の特値
  - 列名やコードの書き方が、この2形式とまったく違う販売管理システム
- 「原因不明の価格差」は、生成したサンプルには1行もありません（手書きのサンプルには1行あります）。実データでは、ここに分類される行の扱いが大事になります。
- 年間影響額は直近12か月の実績で、これからの予測ではありません。
- 正解データは架空の会社（架空商事株式会社）のものです。実在の企業・取引とは関係ありません。
