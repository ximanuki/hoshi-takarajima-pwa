# 見積考古学（estimate-archaeology）v0

過去の見積データから、その会社の**決まった計算ルール**（単価表・掛率・最低料金・端数処理・改定日など）を復元し、
ルールから外れた見積を**検出して分類**する Python パッケージです。

- 入力: 見積台帳の CSV と、列の意味を書いた設定ファイル（JSON。PyYAML があれば YAML も可）
- 出力: `rules.json`（機械可読のルール）、`rules_ja.md`（人が読める仕様書）、`predictions.csv`（1件ごとの判定と根拠）、`coverage.md`（再現率と内訳）
- 結果は「**N件中M件を円単位で再現**」の形で示します。復元するのは「**過去データと矛盾しない最小のルール**」です。

> English: [README.en.md](README.en.md)

## 立ち位置: LLM は提案、決定的エンジンが検証

- v0 は LLM を一切呼びません。金額の計算・パラメータの推定・逸脱の判定は、すべて決定的な計算（numpy）です。
- 人や LLM が関わるのは「列の意味を書いた設定（config）」と「候補の追加（extensions）」だけです。どちらも**候補**にすぎず、
  採用するかどうかは「過去の見積を1円単位で再現できる件数が増えるか」で機械的に決まります。
- 同じ環境・同じ入力からは同じ出力になります（乱数は固定シード、探索の打ち切りは経過時間ではなく計算量で決め、BLAS は1スレッド）。経過時間の上限（既定1時間）は安全装置で、発動した場合は `rules.json` の `meta.search_variants` に記録します。

## 仕組み

```
CSV ──正規化──▶ 税抜金額の候補 ──探索（MDL）──▶ 近似ルール ──厳密化──▶ 円単位のルール ──▶ 逸脱の分類 / 判定停止
```

1. **正規化**（`normalize.py`, `dataset.py`）
   金額の表記ゆれ（`¥12,300-`、全角、`1万2300円`、`一万二千三百円`）、税表示（税込／税抜／税別／内税／外税）、
   税表示がない場合（税抜・税込の両方を候補に残し、ルールとの整合で決める）、消費税額の列、和暦・Excel シリアル値の日付。
   税率は日付で切り替え、税込⇔税抜は有理数で厳密に計算します。
2. **ルールの部品（DSL）**（`program.py`）— JSON で保存でき、日本語の仕様書に変換できます。
   固定費・数量単価・面積単価、区分ごとの単価表、段階（しきい値）、パック／枚数単位の切り上げ、
   **区分ごとの入り数による切り上げ（面付け・歩留まり型の材料費）**、最低数量、得意先区分・得意先ごとの掛率、
   カテゴリや備考のキーワードで付く加算・割増、最低料金（掛率の前／後）、端数処理（単位と方式。担当者の列ごとの例外も可）、
   **改定日つきの版管理された単価表**。
3. **探索**（`search.py`）
   区分（品目など）ごとに、主効果の豊富なモデルを頑健回帰（Cauchy 損失の IRLS）で当てはめ、MDL（パラメータのビット数＋残差のビット数）で
   前向き追加・後ろ向き削除を繰り返して**短いプログラム**を選びます。
   - 掛率は、まず「素の見積」（最も多い得意先区分・備考キーワードなし・再発行でない）だけで当てはめた加算モデルと比べて読み取ります（掛率で歪んでいない価格と比べるため）。
   - 改定日は月初ごとの分割を直接走査し、段階（しきい値）は設定に書かれていない数値列でも、残差の切れ目から候補を作ります。
   - 前向き追加は、誤差が大きいうちは誤差の大きさに合わせた粗い精度で評価し、当てはまるにつれて1円単位の精度に戻します（粗から細へ）。
   - 探索は途中の選択に敏感なので、設定を少しずつ変えた**複数の探索（variants）を並列に走らせ**、区分ごとに最も多く再現した探索の結果を組み合わせ、
     他の探索が見つけた項目も1つずつ試します（どちらも全体の再現件数が増える場合だけ採用。各探索の結果は `variants/` に残します）。
4. **厳密化**（`exact.py`）
   決定的な評価器（過去の見積を何件ぴったり再現するか）だけを基準に、各パラメータを「件数が減らない範囲で最も丸い数」へ寄せ、
   端数処理（方式ごとにパラメータを寄せ直して比較）・税の丸め・最低料金・パックの大きさ・改定日を決めます。
   同じ基準で、しきい値の位置の微調整（例: 取付高さ 3m 以上 → 4m 以上）、2つの表の統合（厚み別＋片面/両面別 → 厚み×面）、
   他の区分と共通の加算（配送料など）の取り込み、欠けている加算・掛率の発見（再現できない見積の多くが同じ丸い値を指すか）も行います。
   再現件数が変わらないなら短いほうのルール（改定日・項目・掛率表を削る）を選びます。
   過去データで決められない値（例: 一度も発動していない最低料金）は推測せず **「要聞き取り」** として、矛盾しない範囲だけを示します。
5. **逸脱の分類**（`classify.py`）— 1か所だけ変えて評価器を回し直し、ぴったり一致した理由を根拠として残します。
6. **判定停止** — 円単位の再現率がしきい値（既定 0.80）未満なら、逸脱の分類を出さず「判定保留（規則不足のため判定停止）」にして、
   再現できない見積がどこに偏っているか（＝足りないルールの手がかり）を `coverage.md` に書きます。

### ルール逸脱の検出と分類

| class | 意味 | 根拠の例 |
|---|---|---|
| `stale_table` | 改定後なのに改定前の単価表で計算 | 改定前（2024-04-01 より前）の単価表で計算すると一致 |
| `copied_rate` | 別の得意先・区分の掛率を流用 | 区分 D の掛率 0.85 を当てると一致 |
| `undocumented_discount` | 記録のない値引き | 規則の金額から 5% 引き、条件の記録なし |
| `typo` | 数字の入れ替わり・桁の脱落など | 規則どおりなら 13,500 のところ 15,300 と記載 |
| `unrecorded_surcharge` | 条件の記録がない割増 | 特急の係数（×1.3）と同じ割増が、その条件の記録なしで適用 |
| `rounding_inconsistency` | 端数処理の方式・単位が違う | 100円未満を四捨五入にすると一致 |
| `revision_or_duplicate` | 再発行・重複 | 再発行見積：元見積と同額のまま仕様が変わっている |
| `unexplained` | 原因不明（規則との差だけ示す） | 規則では 12,300円、記載は 11,000円 |

1件ごとの `status` は `reproduced`（再現）/ `deviation`（逸脱・分類あり）/ `unexplained`（原因不明）/ `abstained`（判定保留）です。
集計は単価表の版・期間（四半期）・得意先区分の単位で行い、**担当者別の集計はしません**。

## 使い方

```bash
make setup                      # .venv を作り、固定した依存（numpy / pytest / ruff）を入れる
make test                       # テスト（数十秒）
.venv/bin/ea fit --config configs/dev_print.json --quotes devdata/print/quotes.csv --out runs/dev_print
.venv/bin/ea check --rules runs/dev_print/rules.json --config configs/dev_print.json --quotes new.csv --out runs/check
```

主なオプション: `--threshold 0.8`（判定停止のしきい値）、`--stop-scope segment`（区分ごとに停止）、`--extensions DIR`（候補の追加）。

`fit` の出力フォルダには `rules.json` / `rules_ja.md` / `predictions.csv` / `coverage.md` のほか、各探索（variants）の結果を `variants/` に残します。
探索の設定（variants の組み合わせ、計算量の上限など）は設定ファイルの `search` で変えられます（既定値は `config.py` の `DEFAULT_SEARCH`）。

### 設定ファイル（列の意味だけを書く）

```json
{
  "name": "print-shop",
  "columns": {"id": "quote_id", "date": "quote_date", "customer": "customer_code", "rep": "rep",
              "amount": "amount", "tax_label": "tax_label", "tax_amount": "tax_amount"},
  "segment": "product",
  "customer_class": "regex(customer_code, '^(一般|[A-Za-z]+)', 1, 'その他')",
  "revision_id_pattern": "-R\\d+$",
  "derived": {"total_qty": "quantity * kinds", "lead_days": "days_between(quote_date, due_date)"},
  "categorical": ["size", "paper", "colors", "delivery"],
  "numeric": ["quantity", "kinds", "pages", "total_qty"],
  "text": ["notes", "finishing"],
  "thresholds": ["lead_days"],
  "features": ["pages * quantity * kinds"]
}
```

設定には価格を書きません。式は安全な小さな式言語（四則演算、`ceil` `regex` `split` `days_between` `if_` など。属性アクセスや import は不可）です。
将来は LLM が列の説明（SCHEMA など）からこの設定の下書きを作り、エンジンが検証する想定です。
`configs/blind_print.json` と `configs/blind_sign.json` は、目隠し試験用のデータの列定義（`blind/*/SCHEMA.md`）だけを見て書いたものです。

### 拡張（コアを変えずに候補を足す）

`--extensions DIR` で、フォルダ内の `*.json`（設定への追記: 派生列・特徴量・しきい値・キーワード・探索設定）と
`*.py`（`register(registry)` で式の関数や Python の派生列を追加）を読み込みます。コアのファイルは変更しません。
`ea hash-core` でコアの SHA-256 を確認でき、`rules.json` の `meta.core_sha256` と `meta.extensions` に記録されます。
例: [`extensions/dev_print_assisted/`](extensions/dev_print_assisted/)。

## 目隠し試験の結果（2026-10-07）

**1週目の v0 は、目隠しのデータでは使い物になりませんでした。** 下の「開発用データでの結果」は自作の生成器に対する数字で、目隠しでは大きく下がります。

| データ | 開発用データ（自作） | 目隠し・frozen（1回きり） | 目隠し・assisted（同じデータで4回改良、目隠しではない） |
|---|---|---|---|
| 印刷 | 88.8% | 9.4%（2,400件中226件） | 19.5%（469件） |
| 看板 | 56.9% | 4.6%（2,378件中110件） | 5.5%（131件） |

- 4つとも再現率が 80% 未満だったので、判定停止が働き、逸脱の分類は出していません。止めなければ、正しい見積 213〜1,260件に指摘が付いていました。
- 届かなかった理由：自動の探索が弱いこと（分析者が手で書いた式のほうが多く一致した）と、計算した金額に応じて変わる決まり（送料無料の境目、金額による丸めの違い、最低料金の改定）を今の部品で書けないことです。
- 詳しくは [`BLIND_PROTOCOL.md`](BLIND_PROTOCOL.md) と [`reports/blind-week1.md`](reports/blind-week1.md)。

## 開発用データでの結果（dev numbers）

開発用の生成器（`devdata/`。目隠し試験のデータとは無関係）で作った架空の2社のデータでの数字です。
生成器とソルバーを同じ側が書いているので、**仕組みが動くことの確認であって、未知のデータでの精度ではありません**。
全体は [`reports/dev_results.md`](reports/dev_results.md)、復元したルールの例は [`reports/dev/print/rules_ja.md`](reports/dev/print/rules_ja.md)。

| データ | 円単位で再現 | ±1% | 正常見積（文法内）の再現 | 逸脱の検出（適合率 / 再現率） | 判定停止 |
|---|---|---|---|---|---|
| 印刷（dev 設定） | 2,434件中2,180件（89.6%） | 90.1% | 100.0% | 90.6% / 92.4% | なし |
| 印刷（目隠し用の設定。SCHEMA だけから作成） | 2,434件中2,162件（88.8%） | 89.9% | 98.9% | 84.4% / 96.2% | なし |
| 印刷＋拡張（見積日の「日」を候補に追加） | 2,434件中2,278件（93.6%） | 94.0% | 100.0% | 99.4% / 98.7% | なし |
| 印刷（文法外の規則を大幅に増やしたもの） | 2,438件中1,693件（69.4%） | 75.1% | 75.7% | —（判定停止） | 全体停止 |
| 看板（dev 設定） | 2,410件中1,839件（76.3%） | 84.5% | 82.0% | —（判定停止） | 全体停止 |
| 看板（目隠し用の設定） | 2,410件中1,372件（56.9%） | 64.7% | 57.0% | —（判定停止） | 全体停止 |

- 印刷では、改定日（2024-04-01 の単価表改定、2025-01-01 の県外配送料改定）、得意先区分の掛率と個別の掛率、
  配送料が掛率の対象外であること、短納期の ×1.3（「納期まで5日未満」として復元。履歴の日数では「3日以内」と区別できない）、1人の担当者だけ10円単位の端数処理、名刺の最低料金 3,000円を復元しました。
  発動例のない区分の最低料金は「要聞き取り」（矛盾しない上限つき）です。再現できない見積は、ほぼ人の癖を入れたものと、
  設定に「日」の列がないため表せない「チラシの月末3%引き」です（後者は `coverage.md` に「同じ3%引きが85件、見積日が28日以降に集中」というルール候補として出て、人の癖とは判定せず判定保留にします）。
- 拡張で「日」の候補を足すと（コアの SHA-256 は同じ）、エンジンが「チラシで見積日が28日以降なら ×0.97」を見つけ、2,180件 → 2,278件になりました。
- 看板では、袖看板（271件）の面積による段階料金を復元できず、全体の再現率が 80% に届かないため判定停止が働きます。
  しきい値を 0 にして分類させた場合の適合率は 27% で、判定停止が要る状況の例になっています。
- 目隠し用の設定（SCHEMA だけから書いた設定）では、看板の再現率が dev 設定より大きく下がります。候補の特徴量が増えると探索が迷いやすく、
  設定の書き方に結果が左右されることを示しています。
- 秒数は 4 CPU コアで2データを同時に走らせたときの値で、1データ 8〜15分です。

## 制約・既知の限界

目隠し試験後の点検で見つかった問題（未修正）:
- 拡張（extensions）の `derived` は入力の列を上書きでき、エンジンはそれを拒めません。Python の拡張は core の動作を書き換えることもできるので、core のハッシュだけでは「core が固定どおりに動いた」ことの証明になりません。
- 1つの探索で数値計算が失敗すると（`SVD did not converge` など）、全体が止まって何も出力されません。
- `work_budget` は厳密な上限ではなく、予算切れで飛ばした探索の段階は記録に残りません。
- 判定停止は、その再現率を最大化するように当てはめた同じデータで判断しています（取り置きのデータでの確認はしていません）。


- **部品（文法）の外にあるルールは再現できません。** 例: 月末だけの値引き（設定に日付の「日」の列がない場合）、面積の累乗のような連続的な式、複数行の明細を合算してから決まる料金。
  こうした見積は「原因不明」や「判定保留」になり、`coverage.md` の「規則が足りない箇所の手がかり」に偏りとして出ます。拡張（extensions）で候補を足すか、聞き取りが必要です。
- 値は履歴に現れた範囲でしか決められません。一度も発動していない最低料金、件数の少ない区分の単価、改定日の正確な日付（前後の見積の間のどこか）は「要聞き取り」または範囲で示します。
- 単価表のキーは「1列」か「2列の組み合わせ」まで。3列以上の交互作用は探索しません（設定の `derived` で組み合わせ列を作れば扱えます）。
- 段階（しきい値）は、観測値・分位点と、残差の切れ目から作った候補のみ。境界は観測値の間のどこかまでしか分かりません。
- 改定日は月初を候補に探し、厳密化で日単位に動かします。品目ごとにずれた小さな改定や、短期間に何度もある改定は見落とすことがあります。
- 端数処理は「全体」＋「1つの列（担当者など）の値ごとの例外」まで。明細ごとの途中丸め（パック・入り数の切り上げは可）や、明細ごとの消費税計算・軽減税率の混在は扱いません。
- 逸脱の分類は「1か所だけ変えたら一致するか」で判定します。2つの癖が重なった見積は「原因不明」になりやすく、`typo` は記載金額の数字の並びだけで判断します。担当者についての判断はしません。
- 探索は計算量の上限つきで決定的ですが、遅めです（開発用データ約2,400件で1データ8〜15分、4 CPU コアで探索4本を並列）。
- 探索は途中の選択に敏感です。複数の探索の組み合わせで緩和していますが、同じデータでも設定（候補の特徴量）が変わると結果が大きく変わることがあります。
- 開発用の数字は、ルールの形を知っている作者が作ったデータでの値です。未知のデータでの精度を示すものではありません。
- 設定（列の意味）の下書きを LLM が作る部分は v0 には含まれません（設定は人が書く前提）。
- `blind/*/messy/` のような体裁の崩れた Excel（月別シート、見積書の控え、個人メモ）の取り込みは v0 には含まれません（CSV のみ）。
- 掛率は全区分共通の表（得意先・条件ごと）か「区分 × 条件」の表までです。区分ごとに違う得意先掛率は扱いません。

## フォルダ構成

```
src/estimate_archaeology/   コア（normalize, expr, dataset, program, library, search, exact, classify, report, pipeline, cli, extensions）
configs/                    データごとの設定（dev_* は開発用、blind_* は SCHEMA.md だけから作成）
devdata/                    開発用データの生成器（gen_print.py, gen_sign.py）・生成済みデータ・採点（evaluate.py, run_dev.py）
extensions/                 拡張の例
reports/                    開発用データでの結果（dev_results.md / .json）
tests/                      pytest（toyshop: 既知のルールと癖を入れた小さな架空の店）
blind/                      目隠し試験のデータ（core の開発には使っていません。assist/ の拡張は blind のデータを見て作りました）
```
